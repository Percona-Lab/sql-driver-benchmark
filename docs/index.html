SQL Driver Benchmark

How much CPU does the database driver itself burn? Twenty-four MySQL and MariaDB drivers in ten languages ran the same single-threaded workloads against Percona Server 9.7 and MariaDB 12.3. For the same work, the most expensive driver often costs ten to a hundred times the cheapest, in CPU and in memory. Twenty-two frameworks, ORMs and query builders were then measured on top of those drivers: thin layers add little, while loading entities or inserting row by row can cost four to more than a hundred times the driver alone.

AI-generated results. This benchmark was designed, run and analyzed with an AI assistant (Claude). Results and findings have been spot-checked by a person, but not every number and explanation has been verified in detail, and some may be wrong. The code and raw data are published so you can verify anything here; please report problems as issues on GitHub.

The charts show client CPU per operation (user + kernel, whole process, GC and JIT threads included), the median of 5 fresh processes on an isolated core at a fixed 3.9 GHz, measured in steady state; switch to memory to see how much the work itself needed and how far each process grew. Server configuration is identical for every driver. Lower is better. A small number next to a value points to a note under its chart: a caveat, a server-side cause, or a result that is still provisional.

How this was measured
  • One bare-metal host (AMD EPYC 4245P, 32 GB, NVMe), Ubuntu 26.04.1, kernel 7.0. SMT and boost off; the client runs alone on an isolated core, the database on three others.
  • Percona Server 9.7.2-3 and MariaDB 12.3.4 with the same settings: 16 GB buffer pool (all data in memory), binlog off, innodb_flush_log_at_trx_commit=2.
  • Each combination runs as 5 fresh processes; the chart shows the median. Results are steady state: runtimes with a JIT (Java, .NET, Node.js, Ruby YJIT) keep warming up until three iterations agree within 5% (at most 40 iterations or 120 s); the others get two warm-up iterations, which is enough for them.
  • Two extra processes per combination collect hardware counters (instructions, IPC, cache misses), shown in the tooltips. Counters are never attached to timed runs, because counting adds cost to every context switch.
  • Memory comes from a separate pass, one process per combination. Memory for the work is the peak resident memory during an iteration minus the memory at its start; memory growth is the highest peak minus the memory right after connecting, before warm-up. Each client is capped at 8 GB.
  • Every iteration is checked against a checksum computed when the data was loaded, and every result's negotiated TLS state is checked against the intended one.
  • TLS is off except in the TLS variants. "Tuned" means driver or framework settings only; the server is never tuned per driver. Exactly what each stack's tuned configuration changes is listed below and shown when you hover a tuned result.
  • "Not supported" lists combinations a driver cannot run, with its own reason.
