How much CPU does the database driver itself burn? MySQL and MariaDB drivers in C, Go, Java and Python ran the same single-threaded workloads against Percona Server 9.7 and MariaDB 12.3. For the same work, the most expensive driver often costs ten to a hundred times the cheapest.

Every figure is client CPU per operation (user + kernel, whole process, GC and JIT threads included), the median of 5 fresh processes on an isolated core at a fixed 3.9 GHz. Server configuration is identical for every driver. Lower is better. A small number next to a value points to a note under its chart: a caveat, a server-side cause, or a result that is still provisional.

How this was measured
  • One bare-metal host (AMD EPYC 4245P, 32 GB, NVMe), Ubuntu 26.04.1, kernel 7.0. SMT and boost off; the client runs alone on an isolated core, the database on three others.
  • Percona Server 9.7.2-3 and MariaDB 12.3.4 with the same settings: 16 GB buffer pool (all data in memory), binlog off, innodb_flush_log_at_trx_commit=2.
  • Each combination runs as 5 fresh processes; the chart shows the median. Two extra processes per combination collect hardware counters (instructions, IPC, cache misses), shown in the tooltips; counters are never attached to timed runs because counting adds cost to every context switch.
  • Every iteration is checked against a checksum computed when the data was loaded, so no driver can skip work.
  • TLS is off for all tests except the TLS variants. "Tuned" means driver options only (for example rewriteBatchedStatements, interpolateParams, server-side prepared statements); the server is never tuned per driver.
  • "Not supported" lists combinations a driver cannot run, with its own reason. Phase 2 adds Node.js, PHP, Ruby, .NET, Rust and C++.
  • Numbered notes mark results with a known caveat. Java results are provisional: they were measured with a fixed warm-up that did not reach steady state; a rerun that warms up until iterations agree within 5% is under way.
